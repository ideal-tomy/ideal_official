# デモ紹介LP ブロック定義書 v1.0

> 1デモ = 1LP を量産するための共通構造定義。
> GembaShift「社内ナレッジAI」LP をリファレンス実装として分解・抽象化したもの。
> 各デモの要件書は、本書への穴埋め（`demo-lp-brief-template.md`）として作成する。

---

## 0. 本書の使い方

```
本書（構造の定義）
  ↓ 穴埋め
demo-lp-brief-template.md（デモ1本ぶんの要件）
  ↓ 実装指示
lp.config.ts + 共通エンジン
  ↓ ビルド
/demo/{slug}/  （単独送付可能なLP）
```

**重要**: 本書はコピーライティングの型ではなく、**答えるべき問いのリスト**である。
各ブロックには「顧客の頭の中にある問い」が1つ紐づく。その問いに答えられないデモは、
LP化がまだ早い＝デモ側の設計に穴がある、と判定する（→ §5 品質ゲート）。

---

## 1. 設計原則

| # | 原則 | 意味 |
|---|---|---|
| P1 | **単一ソース** | LPの数字・文言はデモCONFIGとROI CONFIGから派生させる。LP側で数字を持たない |
| P2 | **除外の明示** | 「効かない場合」を必ず書く。全方位に売り込むLPより、絞って外すLPが刺さる |
| P3 | **主語は顧客** | 「私たちは〜できます」ではなく「御社の〜が〜になります」で書く |
| P4 | **試算は試算と書く** | 金額・削減率には必ず「想定モデルによる試算／効果の保証ではありません」を併記 |
| P5 | **体験への導線** | 資料請求で終わらせない。「その場で触れる」が最大の差別化。CTAは常に二段 |
| P6 | **ブランド非依存** | Coreにブランド名を直書きしない。AXEON/ideal は Brand Config で切替 |

---

## 2. CONFIG階層

既存のデモ側3層（Brand → Workflow → Sample Data）に、LP層を**兄弟として**接続する。
LPを別リポ・別データで持つとデモ更新時に必ずズレるため、必ず同一ソースから派生させること。

```
Brand Config        … ロゴ / 社名 / カラートークン / 会社情報 / フォーム送信先
      ├─ Demo Config      … デモの機能・ステップ・サンプルデータ（既存）
      ├─ ROI Config       … 前提値・単価・計算式・スライダー定義（既存ツール）
      └─ LP Config        … 本書のブロックへの穴埋め ← 今回新設
                             ※ 数字は ROI Config を参照。LP側に直値を書かない
```

### 2.1 ブランド切替で変わるもの / 変わらないもの

| 変わる | 変わらない |
|---|---|
| ロゴ・社名・カラー・フッター会社情報 | ブロック構成・順序 |
| フォーム送信先・問い合わせ導線 | 本文コピー（デモ固有のため） |
| 「私たち」の一人称表現 | ROI計算式 |
| プライバシーポリシーURL | デモ体験リンク（共通デモを指す） |

## 3. ブロック定義

**必須度**: ◎=全デモ必須 / ○=原則入れる（外す場合は理由を要件書に記載） / △=デモ特性により省略可

---

### B00 ヘッダー ◎

| 項目 | 内容 |
|---|---|
| 問い | （なし。常時表示のナビゲーション） |
| 役割 | ブランド提示 + CTAの常時露出 |
| 必須要素 | ロゴ（Brand Config）／デモ名／固定CTAボタン1つ |
| CONFIG | `brand.logo`, `lp.demoName`, `cta.primary` |
| 執筆ルール | メニューリンクは置かない。スクロールを妨げるものは全部落とす |

---

### B01 ヒーロー ◎

| 項目 | 内容 |
|---|---|
| **問い** | 「いま何が奪われているのか」 |
| 役割 | 3秒で「自分の話だ」と認識させる |
| 必須要素 | ① 一行の断定コピー（例: 答えは、もう社内にある。）<br>② 損失を示すサブコピー（例: たどり着けないまま、毎日お金が消えている）<br>③ 3〜4行の状況説明<br>④ CTA 2つ（**試算する** / **仕組みを見る**）<br>⑤ 安心バッジ3つ（無償・NDA・準備不要 等）<br>⑥ 成果物ビジュアル（デモ画面のモック） |
| CONFIG | `hero.headline`, `hero.subline`, `hero.body`, `hero.badges[]`, `hero.visual`, `cta.primary`, `cta.secondary` |
| 執筆ルール | ・見出しは製品説明にしない。**顧客の状態**を言う<br>・「AI」を主語にしない<br>・ビジュアルには必ず「※画像はイメージです」 |
| 注意 | ヒーローのCTAは「相談」ではなく**「試算」「体験」**にする。心理的コストが低い方が押される |

---

### B02 数字インパクトバー ◎

| 項目 | 内容 |
|---|---|
| **問い** | 「で、いくらの話なのか」 |
| 役割 | 読ませる前に規模を叩き込む |
| 必須要素 | ① 主要損失額の一文（例: 年間8,000万円が消えている計算に）<br>② 計算根拠の注記（1人◯分/日・時給◯円・◯営業日）<br>③ 指標カード4枚（速さ / 準備 / 費用 / 回収期間） |
| CONFIG | `impact.mainFigure`（**ROI Config から算出**）, `impact.basis`, `impact.metrics[4]` |
| 執筆ルール | ・主要数字は必ずB11のシミュレーター初期値と一致させる（P1）<br>・指標カードは「0分」「¥0」のようにゼロを混ぜると効く<br>・回収期間は幅で書く（3〜4ヶ月） |

---

### B03 価値の3本柱 ○

| 項目 | 内容 |
|---|---|
| **問い** | 「結局、何をしてくれるのか」 |
| 役割 | 詳細に入る前の要約。ここだけ読んでも通じる状態にする |
| 必須要素 | カード3枚（アイコン / 見出し2行 / 本文3〜4行、キーワードをハイライト） |
| CONFIG | `pillars[3]{icon, title, body, highlight[]}` |
| 執筆ルール | 3本の軸は **「読める」「正しい」「試せる」** のように性質を変える。同じ方向の3つは無意味 |

---

### B04 コストの正体 ◎

| 項目 | 内容 |
|---|---|
| **問い** | 「なぜ今まで解決できなかったのか」 |
| 役割 | 痛みを分解して自覚させる。**課題の解像度で信頼を取る**ブロック |
| 必須要素 | ① セクションラベル + 見出し<br>② コスト/課題カード 4枚（番号付き・各2〜3行）<br>③ 挿絵<br>④ **共通点をまとめる帯**（4つを1文に束ねる） |
| CONFIG | `problem.label`, `problem.headline`, `problem.items[4]{no, title, body}`, `problem.summary` |
| 執筆ルール | ・4つは**種類が違う**こと（探す/聞く/間違える/やり直す のように動詞を変える）<br>・「会計帳簿には出てこないが毎日払っている」型の言い回しが効く<br>・締めの帯で「足りないのは知識ではなく手段」と**論点を移す** |

---

### B05 効く条件 / 効かない条件 ◎

| 項目 | 内容 |
|---|---|
| **問い** | 「これはうちの話なのか」 |
| 役割 | **自己診断による自己説得**。同時に、合わない見込み客を正直に外す |
| 必須要素 | ① 条件カード3枚（番号 / 条件 / 補足2〜3行）<br>② 「3つ当てはまるなら、この仕組みは御社のために設計されています」<br>③ **除外の一文**（例: 「だいたい合っている」で足りる用途なら一般的なRAGで十分です） |
| CONFIG | `fit.conditions[3]{no, title, body}`, `fit.affirm`, `fit.exclude` |
| 執筆ルール | ・除外文を削らない。ここが信頼の源泉（設計原則P2）<br>・条件は「業種」で切らず**「状態」**で切る（例: 正本がExcel方眼紙の中にある）<br>・ワークフローエンジンの `show_then_exclude` と同じ思想 |

---

### B06 業界別ユースケース ○

| 項目 | 内容 |
|---|---|
| **問い** | 「うちの業界だとどう使うのか」 |
| 役割 | 横展開の証明 + 自業界への翻訳を読者にさせない |
| 必須要素 | ① 見出し（共通する問いの形を提示）<br>② 業界カード4枚（業界名 / 対象文書・対象業務 / **その業界の“ひと言”**（引用調の吹き出し）/ 解説3〜4行）<br>③ その他業界の列挙1〜2行 |
| CONFIG | `usecases[4]{industry, scope, quote, body}`, `usecases_more` |
| 執筆ルール | ・吹き出しは**現場の人が実際に言いそうな一言**にする。ここが刺さりどころ<br>・4業界は既存の商談先／狙う業界に合わせて差替（LP Config で変わる部分）<br>・「どの業界でも問いの形は同じ」と明示して普遍性を担保 |

---

### B07 壁 × 技術 ◎

| 項目 | 内容 |
|---|---|
| **問い** | 「なぜあなた達ならできるのか」 |
| 役割 | 技術的な納得。**同じことを考えて失敗した人**への回答 |
| 必須要素 | ① 「◯つの壁を、◯つの技術で壊します」型の見出し<br>② 概念図（1枚）<br>③ 壁×技術カード 4組（壁ラベル / TECH番号 / 技術名 / 説明3行 / **→ 効果の一行**）<br>④ 「誰もが考えたが、多くがつまずいた」という導入文 |
| CONFIG | `mechanism.headline`, `mechanism.diagram`, `mechanism.items[4]{wall, techNo, techName, body, effect}` |
| 執筆ルール | ・壁と技術は**1対1で対応**させる（壁3つ技術5つ、にしない）<br>・「→」の効果一行はベネフィット言語で（例: 何万ページあっても答えは薄まらない）<br>・実装名・製品名は出さない。**方式**だけ書く |

---

### B08 結果イメージ ○

| 項目 | 内容 |
|---|---|
| **問い** | 「実際、どう見えるのか」 |
| 役割 | B07の抽象を1枚で着地させる |
| 必須要素 | 出力画面モック1枚 + 「◯つの壁を壊すと、こうなります」の導入 + 下部に補足一行（数秒／出典つき／元文書で確認できる） |
| CONFIG | `resultShot.caption`, `resultShot.image`, `resultShot.note` |
| 執筆ルール | モックは**根拠表示・出典リンク・確認済みバッジ**まで描く。ここが「作り込んだ感」を出す |

---

### B09 よくある失敗との違い ○

| 項目 | 内容 |
|---|---|
| **問い** | 「前に試して失敗したのと何が違うのか」 |
| 役割 | 既導入・検討済み層の反論処理 |
| 必須要素 | ① 「◯◯を試して失敗した御社へ」型の見出し<br>② 比較表（比較ポイント 5行 × 一般的手法 / 本手法）<br>③ **フェアネス注記**（一般手法が悪いわけではない、この条件なら十分） |
| CONFIG | `comparison.rows[5]{point, common, ours}`, `comparison.fairnessNote` |
| 執筆ルール | ・競合製品名は書かない。**手法名**で比較する<br>・比較軸に必ず「運用とコスト」を入れる（使うほど安くなる/高くなる の対比は強い）<br>・フェアネス注記を削らない（P2） |
| 省略判断 | 市場に「よくある失敗パターン」が存在しないデモでは省略可 |

---

### B10 育つ / 継続価値 △

| 項目 | 内容 |
|---|---|
| **問い** | 「導入して終わりではないのか。運用が破綻しないか」 |
| 役割 | 単発ツールではない証明。**保守コストへの不安**を潰す |
| 必須要素 | ① 「使うことが、そのまま手入れになる」型の見出し<br>② 循環ステップ3つ<br>③ 挿絵<br>④ 締めの対比2行（放っておくと古びる / 使うほど新しく安くなる） |
| CONFIG | `growth.headline`, `growth.cycles[3]{no, title, body}`, `growth.closing` |
| 省略判断 | 蓄積・学習の性質を持たないデモ（単発変換ツール等）は省略可。<br>ただしその場合、B09の「運用とコスト」行で代替すること |

---

### B11 ROI 60秒試算 ◎

| 項目 | 内容 |
|---|---|
| **問い** | 「いくら返ってくるのか」 |
| 役割 | **自分の数字**にすることで他人事から自分事へ移す |
| 必須要素 | ① 「私たちが盛った数字を見ても意味がありません」型の導入<br>② スライダー4本（人数 / 時間 / 単価 / 削減率）＋各スライダーの注記<br>③ 右パネル: 現在の損失額（年間） / 取り戻せる金額（年間）<br>④ **その場でCTA**（この数字を無償トライアルで実測する）<br>⑤ 試算注記（P4） |
| CONFIG | **ROI Config を直接参照**。`roi.sliders[4]`, `roi.formula`, `roi.defaults`, `roi.cta` |
| 執筆ルール | ・初期値は B02 の主要数字と**必ず一致**させる<br>・スライダー注記で「控えめに見たい場合は下げてください」と誘導すると信頼が上がる<br>・開発費用の概算ロジックを持つデモは、上限値を自動流し込みして回収期間まで出す |
| 実装 | 既存の投資回収シミュレーターを iframe ではなく**コンポーネントとして埋め込む**（数値の単一ソース化のため） |

---

### B12 進め方 ◎

| 項目 | 内容 |
|---|---|
| **問い** | 「何から始めるのか。どこまでタダで、どこから金がかかるのか」 |
| 役割 | 次の一歩の心理的コストをゼロにする |
| 必須要素 | ① 「無償で試して、数字を見てから決める」型の見出し<br>② ステップ3つ（番号 / 見出し / **費用ラベル**（無償・数週間 / ここまで費用ゼロ / 本導入）/ 説明3〜4行）<br>③ 挿絵<br>④ 「合わなければここで終えて構いません」の一文 |
| CONFIG | `process.steps[3]{no, title, costLabel, body}`, `process.exitNote` |
| 執筆ルール | ・**費用の発生点を明示**する。ここを曖昧にすると全部濁る<br>・「順番を逆にしました」＝先に無償で動かす、という構図を言語化する |

---

### B13 FAQ ◎

| 項目 | 内容 |
|---|---|
| **問い** | 「懸念点に先回りして答えているか」 |
| 役割 | 商談で必ず出る質問を先に潰す。**社内稟議の材料**を渡す |
| 必須要素 | アコーディオン 8〜10問。1問目は開いた状態 |
| 必須の質問カテゴリ | ① 適合性（うちのデータ形式でも本当に動くか）<br>② **料金**<br>③ ランニングコスト／従量課金の不安<br>④ 既存環境の変更要否<br>⑤ 精度は何%か<br>⑥ **セキュリティ・情シス審査**<br>⑦ 既存基盤との併用可否<br>⑧ 準備の手間<br>⑨ スモールスタートの可否 |
| CONFIG | `faq[]{q, a, defaultOpen}` |
| 執筆ルール | ・「精度は何%か」には数字で答えず、**答えない設計**（一致しなければ「分かりません」と答える）で回答する<br>・料金を1問目付近に置く。隠すと不信になる |

### B14 最終CTA + フォーム ◎

| 項目 | 内容 |
|---|---|
| **問い** | 「いま動く理由は」 |
| 役割 | 損失の継続性を再提示してコンバージョン |
| 必須要素 | ① 左: 締めコピー（例: このコストは、今日も発生しています）+ 安心3点<br>② 右: フォーム（会社名 / お名前 / メール / ご相談内容 任意 / プライバシー同意）<br>③ 「入力は1分。1営業日以内にご連絡します」<br>④ **体験導線の併記**（P5: フォームとは別に「今すぐデモを触る」を置く） |
| CONFIG | `finalCta.headline`, `finalCta.assurances[3]`, `form.fields[]`, `form.endpoint`（**Brand Config**）, `form.privacyUrl`（**Brand Config**） |
| 執筆ルール | フォーム項目は5つまで。役職・電話番号は取らない（離脱要因） |

## 4. 標準ブロック順序

```
B00 ヘッダー
B01 ヒーロー              ← 何が奪われているか
B02 数字インパクトバー     ← いくらの話か
B03 価値の3本柱           ← 何をしてくれるか
── 課題の解像度 ──
B04 コストの正体           ← なぜ解決できなかったか
B05 効く条件/効かない条件   ← うちの話か
B06 業界別ユースケース      ← うちの業界では
── 解決の納得 ──
B07 壁 × 技術             ← なぜできるのか
B08 結果イメージ           ← どう見えるか
B09 よくある失敗との違い    ← 前の失敗と何が違うか
B10 育つ/継続価値          ← 運用は破綻しないか
── 意思決定 ──
B11 ROI 60秒試算          ← いくら返るか
B12 進め方                ← 何から始めるか
B13 FAQ                   ← 懸念への先回り
B14 最終CTA + フォーム      ← いま動く理由
```

**順序の入替は原則不可**。「痛み → 自己診断 → 納得 → 数字 → 一歩」の流れが崩れる。
ただしB06・B09・B10は省略可（§3の省略判断に従う）。

## 5. 品質ゲート（LP化の可否判定）

各ブロックの「問い」に**デモの実物で答えられるか**をチェックする。
不足がある場合、LP制作ではなく**デモ側の改修**が先。

| ゲート | 判定基準 | 不合格時の対応 |
|---|---|---|
| G1 | B04の課題4つを、業界の実務語で書けるか | ヒアリング不足。商談メモから抽出 |
| G2 | B05の「効かない条件」を書けるか | 適用範囲が未定義。デモのスコープを先に決める |
| G3 | B07の壁と技術が1対1で対応するか | 技術的な差別化が曖昧。方式を言語化する |
| G4 | B08の出力モックが実物と一致するか | デモ側のUI未完成。**LP先行禁止** |
| G5 | B11の計算式にROI Configがあるか | ROI CONFIGを先に作る |
| G6 | B13の「料金」に答えられるか | 概算見積もりロジック未整備 |

## 6. 実装要件（共通）

### 6.1 配信・URL

| 項目 | 仕様 |
|---|---|
| URL | `/demo/{slug}` に統一（後からどのサイトにもマウント可能に） |
| 生成単位 | 1LP = 1独立ビルド。単独送付を主目的とする |
| OGP | 必須。デモ名 + 主要数字 + ブランドロゴを含む画像を自動生成 |
| noindex | Brand/LP Config のフラグで切替（個別送付版は検索非表示） |
| 計測 | 送付先識別のため `?ref={client-slug}` を受け、閲覧到達点を記録 |

### 6.2 表示要件

- **iOSダークモード対策 3層必須**
  1. `<meta name="color-scheme" content="light">`
  2. CSS で `color-scheme: light only`
  3. `@media (prefers-color-scheme: dark)` でライトパレットを明示上書き
- **日本語見出しの改行崩れ対策**: `word-break: auto-phrase` / `line-break: strict` / `text-wrap: balance`
- **スマホ基準幅 370px** でレイアウトを設計・検証
- 図版・イラストの日本語フォントは **Noto Sans CJK JP**

### 6.3 CTA設計（二段構え）
