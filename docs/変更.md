# セキュリティ監査依頼｜公開Webサイト・API・DB・メール

## 1. 目的

現在公開・運用している以下の4案件について、セキュリティの現状調査を実施してください。

対象：

1. ideal（ideal-dao.com）
2. AXEON（axeon.jp）
3. サンリットウエスト（対象URL・リポジトリは調査して特定）
4. ダーツトーナメントシステム（ideal-tomy/tournament）

今回の目的は、セキュリティ対策の実装ではありません。

**現在どのような仕組みで動作しているか、どのような対策が実施されているか、どこに問題や未確認事項があるかを正確に把握することです。**

調査結果はMarkdown形式で保存し、今後の改善計画と修正履歴の基礎資料として使用します。

---

## 2. 最重要ルール

### 調査のみ実施

今回、以下の作業は禁止します。

- ソースコードの変更
- 環境変数の追加・変更・削除
- GitHubへのPush
- Vercel・Cloudflareへのデプロイ
- Firewall・WAF・ルーティング設定の変更
- DBの書き込み・削除
- メールのテスト送信
- Webhookへのテストリクエスト
- 本番APIに対する負荷テスト
- 既存の認証・アクセス制限の解除

すべて読み取り専用の調査としてください。

### 推測と事実を区別する

調査結果には、必ず以下のいずれかの判定を付けてください。

- **確認済み**：コードまたは実設定で確認できた
- **問題あり**：具体的な問題を確認した
- **要検証**：実装はあるが、本番での動作は未確認
- **未確認**：権限不足・資料不足などで調査できなかった
- **対象外**：その案件には該当機能がないことを確認した

未確認の項目を「安全」「問題なし」と記載しないでください。

すべての指摘に、根拠となるファイルパス、行番号、設定項目、確認方法を記載してください。

秘密鍵・APIキー・パスワード・トークンの値はレポートに記載しないでください。

## 3. 調査対象と内容

### A. 公開Webサイトのセキュリティ

各サイトについて以下を調査してください。

- HTTPSとTLSの設定
- HTTPからHTTPSへのリダイレクト
- セキュリティヘッダー
- CORS設定
- Content Security Policy（CSP）
- 公開不要ファイル・デバッグ情報の露出
- 管理画面の公開範囲
- エラーメッセージからの内部情報漏えい
- 使用フレームワークと依存ライブラリ
- 既知の脆弱性と更新状況
- GitHubリポジトリの公開範囲
- GitHub ActionsなどのCI/CD権限

### B. APIのセキュリティ

すべてのAPIエンドポイントを洗い出してください。

各APIについて以下を確認します。

- URL・HTTPメソッド
- 用途
- 認証の有無
- 認可・権限チェック
- 入力バリデーション
- レート制限
- CSRF対策の必要性と実装
- CORSの設定
- エラーハンドリング
- ログへの個人情報出力
- 外部APIとの通信
- APIキーの管理方法
- APIの直接呼び出しによる操作可能範囲

特に、フロントエンドでボタンを非表示にしているだけで、API側の権限制御が存在しない箇所がないか確認してください。

API一覧表を作成し、認証・認可・レート制限の実装状況を記録してください。

### C. データベースのセキュリティ

Supabase・Firebase・Cloudflare D1など、使用しているDBを特定してください。

確認項目：

- DBの種類と利用目的
- 認証方式
- 読み取り・書き込み権限
- RLSや同等のアクセス制御
- 管理者権限と一般利用者権限の分離
- APIからのDB操作
- 個人情報の保存状況
- バックアップと復元手段
- DB接続情報の管理
- 不要な公開設定
- データ保持・削除方針

RLSが存在しない場合でも、サーバー側で適切にアクセス制御されているかを確認し、仕組みに応じて評価してください。

### D. 問い合わせフォーム・メールのセキュリティ

**この項目はideal・AXEON・サンリットウエストで重点的に調査してください。**

#### 問い合わせフォーム

- フォームの設置場所
- 送信先API
- Turnstile・reCAPTCHAなどの有無
- ハニーポットの有無
- レート制限
- 入力バリデーション
- ボットによるAPI直接送信への対策
- 送信失敗時の処理
- スパム判定後の処理
- 本番環境での有効性

#### メール送信経路

フォーム送信後の処理を最後まで追跡してください。

例：

フォーム
→ API
→ Webhook
→ Zapier / Google Apps Script / メールサービス
→ 管理者通知・自動返信

確認項目：

- どのサービスがメールを送信しているか
- 管理者への通知先
- 問い合わせ相手への自動返信の有無
- From / Reply-Toの設定
- 第三者のメールアドレスを使った大量送信の可能性
- Webhook URLの管理方法
- Webhookの認証・署名検証
- メール送信回数の制限
- メール送信失敗時の処理
- 個人情報の転送先
- メール本文のHTMLエスケープ
- メールヘッダーインジェクション対策

Webhookの転送先が確認できない場合は、その時点で調査完了とせず、追跡に必要な情報を未確認事項として列挙してください。

#### メールドメイン認証

以下を調査してください。

- SPF
- DKIM
- DMARC
- MXレコード
- メール送信元ドメイン
- SPFの重複・設定不備
- DMARCのポリシー
- Google Workspaceなどのメールサービス設定

DNSの公開情報で確認できる項目と、管理画面でしか確認できない項目を分けて報告してください。

メールの送信テストは実施しないでください。

### E. Vercelのセキュリティ

対象となるVercelプロジェクトを特定してください。

- 本番ドメインと接続プロジェクト
- Productionブランチ
- デプロイ設定
- 環境変数の登録状況（値は表示しない）
- Production / Preview / Developmentの分離
- Deployment Protection
- Firewall・WAF
- レート制限
- アクセスログ
- 不要な公開API
- 過去のデプロイURLへのアクセス制御
- デプロイ権限
- GitHub連携設定

#### idealの特別確認

idealでは、フォームスパムへの緊急対策として `/api/contact` をHTTP 503で停止していました。

以下を必ず確認してください。

1. 503停止ルールが現在も有効か
2. Turnstile実装が本番に反映されているか
3. Upstash Redisによるレート制限が本番に反映されているか
4. 必要な環境変数が登録されているか
5. 本番デプロイとGitHubの最新コードが一致しているか
6. 503停止解除に必要な条件がそろっているか

**503停止ルールは絶対に解除しないでください。**

### F. Cloudflareのセキュリティ

Cloudflareを利用している案件について確認してください。

- DNS
- SSL/TLS
- WAF
- Bot対策
- Turnstile
- Workersの公開ルート
- Workers Secrets
- API認証
- リクエスト制限
- D1アクセス権限
- R2バケットの公開設定
- カスタムドメイン
- ログ・監視
- 使用量・課金上限
- バックアップ・復旧

### G. トーナメント専用調査

トーナメントシステムについては、通常のWebサイトとは別に以下を重点調査してください。

#### 写真・ファイル

- 写真アップロードの認証
- アップロード可能な利用者
- ファイル形式・容量制限
- MIMEタイプと実ファイル内容の検証
- ファイル名・保存パスの安全性
- 他人の写真の上書き・削除防止
- R2の公開範囲
- 署名付きURLの使用状況
- 不正ファイルアップロード対策
- 保存した写真の削除・保持方針

#### トーナメント運営

- イベント管理者の認証
- 参加者の操作権限
- 観客画面の読み取り専用制御
- 試合結果の更新権限
- ペア決定・勝敗確定の操作権限
- リアルタイム更新の認証
- イベントIDの推測による情報取得
- 他イベントへの不正アクセス
- 二重送信・同時更新によるデータ不整合
- 管理者トークンの漏えいリスク
- 通信切断時の復旧
- イベント当日の障害対応

既存プロジェクトのアプリケーションコードには変更を加えないでください。

## 5. 各レポートの必須構成

各Markdownファイルは、以下の構成で統一してください。

### 1. 調査概要
- 対象案件
- 対象URL
- リポジトリ
- 調査日時
- 調査範囲
- 調査方法

### 2. 現在の構成
- 使用技術
- 外部サービス
- データの流れ
- 認証・権限の仕組み

### 3. 実装済みの対策
確認できた内容と根拠。

### 4. 発見した問題
各問題に以下を記載。

- ID
- 問題の内容
- 重大度（緊急・高・中・低）
- 根拠
- 想定される影響
- 推奨する対応
- 判定状況

### 5. 未確認事項
- 確認できなかった理由
- 追加で必要な情報
- 確認するための具体的な手順

### 6. 推奨改善案
- 緊急対応
- 短期対応
- 中長期対応

### 7. 検証方法
修正後にどのような確認が必要か。

---

## 6. 横断的なリスク管理表

`02-risk-register.md` には、4案件の問題を横断して記録してください。

各問題に一意のIDを付け、次の情報を含めてください。

| ID | 案件 | 分野 | 問題 | 重大度 | 根拠 | 対応方針 | 状態 |
|---|---|---|---|---|---|---|---|

重大度は、影響範囲、悪用の容易さ、公開状況、扱う情報の重要性を根拠に判断してください。

根拠のない点数化はしないでください。

## 7. 調査の進行順

次の順番で進めてください。

1. ideal
2. トーナメント
3. AXEON
4. サンリットウエスト

最初に各案件のリポジトリ・公開ドメイン・インフラを特定してください。

アクセス権限が不足している場合、推測で補わず、必要な権限や確認方法を報告してください。
