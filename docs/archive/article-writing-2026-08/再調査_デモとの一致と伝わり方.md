# 再調査 ― 説明文とデモは合っているか、経営者に伝わるか

## この記事群がやろうとしていること

```
よくある悩み  →  説明文で「うちの課題はこれだ」と分かる  →  デモで「こう解決するのか」と分かる
```

この三段のうち、いま**二段目までは成立しています。**
問題は三段目、デモに渡すところで起きています。

---

## 第1部　説明文とデモの中身は合っているか

デモ資産マスターの記載と、記事の文面を一件ずつ突き合わせました。

### 建設 → 現場写真から報告書（ocr-demo）

| 記事が言っていること | デモの実際 | 判定 |
|---|---|---|
| 写真を選ぶところから、中身を直して出すところまで | 画像投入 → 下書き → 編集 → 確認 → 提出 → PDF | ○ |
| 用意したサンプル写真で動きます | API不要のサンプルあり | ○ |
| 自分の写真を入れて試せます | 実AI生成に対応 | ○ |
| 2分ほど | 妥当 | ○ |

**問題が一つあります。デモは写真が最大5枚までです。**

記事を読んだ社長が思い浮かべているのは、一つの現場で撮った何十枚、何百枚です。
「写真を整理して報告書にする仕事」と書いてあるので、当然そう読みます。
そこで開いて5枚までだと、その場で「これは違うな」と思われます。

対応は二つです。

- 記事側に「まずは5枚で試してください」と先に書く
- デモ側の上限を上げる

先に書くほうが早いです。書いてあれば、5枚でも試してもらえます。

**もう一つ。デモには朝礼メモを作るモードもあります。**
記事は報告書の話しかしていないので、これは触れずに終わっています。
朝礼の下書きは、現場所長にはかなり刺さる機能です。もったいない。

### 建設の後半3つのリンク

| 記事の書き方 | デモの実際 | 判定 |
|---|---|---|
| 写真・報告・管理を通しで見る | 写真分類、報告書、管理画面の3体験 | ○ |
| 現場・監督・内勤の3つの立場で動かす | 3ロールのアカウントで実際に動く | ○ |
| 協力会社の選び方と評価 | 業者の点数づけ、選定の相談 | △ |

三つ目だけ注意が要ります。**このデモの相談機能は、AIではなく決まったルールで動いています。**
飲食のシフトでは「AIではありません」と正直に書いているのに、
ここでは何も書いていないので、記事群の中で扱いが揃っていません。

### 製造 → ナレッジの画面（product_flow）

| 記事が言っていること | デモの実際 | 判定 |
|---|---|---|
| 用意したサンプルの手順書と検査記録で動きます | サンプルあり | ○ |
| **自社の文書を入れて試すこともできます** | 資産マスター上「公開投入の画面は要確認」 | **要確認** |
| 工程デモ / 品質保証デモ / 記録デモ の3つに分かれる | 一つのハブの中の別々のパック | △ |

**「自社の文書を入れて試せます」は、書いてしまって大丈夫か確認が必要です。**
資産マスターでは、その画面が公開されているかどうかが未確認のままになっています。
開いて入れられなかった場合、いちばん失いたくない場面で信用を落とします。

**3つのリンクの見せ方も直したほうがいいです。**
記事は工程・品質・記録が別々のデモのように書いていますが、
実際は一つのハブの中身です。しかも記録デモは建設向けに作ったものなので、
製造の社長がクリックすると建設現場の画面が出ます。ここは説明が要ります。

### 医療・介護 → ケア記録（kaigo_operation_demo）

| 記事が言っていること | デモの実際 | 判定 |
|---|---|---|
| その場で声に出したものが記録の形になる | ブラウザの音声入力 → 構造化 → 送信 | ○ |
| 3つの画面がつながっている | 現場・内勤・医療連携が連動 | ○ |
| 声を記録にする部分は仮の仕組み | 構造化はモックのロジック | ○ 正直で良い |

**内容としては、6本でいちばんよく合っています。**

ただし、実務上の落とし穴が一つあります。
**このデモの音声入力は、ブラウザの機能を使っています。**
つまり、iPhoneのSafariで開いた施設長が、マイクを押しても動かない可能性があります。

記事には「スマホで試せます」とは書いていませんが、
「その場で声に出す」と書いてあるので、当然スマホで試そうとします。
そこで動かないと、この記事の主役の機能が試せないまま終わります。

対応: 「パソコンのChromeでお試しください」と一行入れる。
または、音声が使えない場合は文字入力でも同じ結果が見られる、と書く。

### 保育 → ケア記録の記録部分

記事は「保育向けではありません」と正直に書いています。ここは良い判断です。

**ただし、開いた先の画面には保育の要素が一つもありません。**
訪問看護、医師への依頼、利用者という言葉が並びます。
園長が見て「これは自分の仕事とは別物だ」と判断する可能性が高いです。

記事では記録部分だけを見てほしいと書いていますが、
デモ側には「記録だけ見る」入口がありません。
最低限、どの画面のどこを見ればいいかを、記事側で指定する必要があります。

例:「最初に出てくる画面の、マイクのボタンだけ押してみてください」

### 小売 → 問い合わせ対応（customer_support_demo）

| 記事が言っていること | デモの実際 | 判定 |
|---|---|---|
| お客さまとして質問してみる | 顧客側の画面あり | ○ |
| 裏側で何を見て答えたのか表示 | 説明モードで仕組みを表示 | ○ |
| 自社のFAQを入れて試す | 自分のFAQ・カタログを入れられる | ○ |
| 答えられない質問は人へ回す | 有人への引き渡しあり | ○ |

**6本の中で、説明文とデモが最もよく一致しています。**
記事の3ステップが、そのままデモの3段階に対応しています。

一点だけ。**「登録は要りません」の範囲を確認してください。**
このデモには、体験コードや自分の鍵を使う本格的な段階があります。
サンプルの範囲だけなら登録不要ですが、自社FAQを入れる段階でコードが必要なら、
記事の「登録は要りません」と食い違います。

### 飲食 → シフト管理（shift_demo）

| 記事が言っていること | デモの実際 | 判定 |
|---|---|---|
| 希望を出す→案が出る→差し替え→確定→既読 | すべてあり | ○ |
| 当日の欠勤を入れて埋め直せる | 欠勤の穴埋めあり | ○ |
| スタッフ・店長・経営の3画面 | 3面あり | ○ |
| 決まったルールで計算。AIではない | その通り | ○ |

**完全に一致しています。6本の手本にできます。**

労働時間の注意表示や複数店舗への対応もデモにありますが、記事では触れていません。
複数店舗を持つ社長には効く部分なので、一行足す価値があります。

### 飲食の後半 → 電話をチャットで受ける（assist_demo）

記事「まだAIにはつないでいない試作です」= その通りです。正直で問題ありません。

## 第2部　リテラシーが低い人にとっての障害

### デモに行き着く前の壁

**「デモ」という言葉が分からない。**
6本すべてで使っています。展示会で聞いたことはあっても、
自分が操作するものだとは思っていません。「見せられるもの」だと思うと、押しません。

**押したあと何が起きるか書いていない。**
別の画面に飛ぶのか、ダウンロードが始まるのか、
自分の会社の情報を入れさせられるのか。分からないと押しません。

一行足すだけで変わります。
「新しい画面が開きます。会社名や連絡先を入れる必要はありません。」

### デモに着いたあとの壁

**何をすればいいか分からない。**
どのデモも、開くと画面が出ます。ですが、ITに慣れていない人は
「どこを押せばいいのか」で止まります。

記事側で最初の一手を指定してください。

- 建設「まず、青いボタンで写真を3枚選んでください」
- 飲食「まず、店長の画面から入ってください」
- 小売「まず、お客さまの気持ちで質問を打ってみてください」

**戻り方が分からない。**
デモに飛んだあと、記事に戻ってこられないと、そこで終わりです。
別タブで開くようにするか、デモ側に戻る導線が要ります。

## 第3部　営業マンの日本語になっているか

### いまの文章は、評論家の口調です

6本を通して、こういう言い方が多く出てきます。

| いまの書き方 | 営業マンなら |
|---|---|
| 〜という話ではありません | 〜ではありません。ここは正直に申し上げます |
| 実際には大きく効きます | ここがいちばん効きます |
| 〜が生まれています | 〜が起きています |
| 見るべきは補助率ではなく | 補助率よりも、先に見ていただきたいのは |
| 判断を間違えます | 判断を誤ることがあります |
| 使われません | 使ってもらえません |

違いは主語です。評論家は現象を主語にします。営業マンは相手を主語にします。

### 言い切るところと、和らげるところを分ける

営業の日本語には決まりがあります。

**言い切っていいもの**
- 事実（デモで何ができるか、何ができないか）
- 自分たちの姿勢（ここは正直に申し上げます）

**和らげるべきもの**
- 相手の会社の状況の決めつけ
- 相手が過去にやったことの否定

いまの記事は、これが逆になっている箇所があります。

例（製造）:
> 一人になった時点で、その工程は会社の資産ではなく、その人の私物になります。

言っていることは正しいのですが、社長からするとベテラン職人を否定されています。
営業がこれを口に出すことはまずありません。

直し例:
> その方が休まれると止まってしまう。これは会社としては、かなり重い状態です。

例（建設）:
> 紙をやめないまま新しい入力を足すのが、いちばん確実な失敗です。

直し例:
> 紙を残したまま入力を足すと、まず続きません。一つ足すなら、一つやめる。ここだけは徹底してください。

### 「ですます」の中に、話し言葉を少し混ぜる

いまは全文がきれいな書き言葉です。読みやすいのですが、少し硬い。
営業の日本語は、要所で話し言葉に落ちます。

- 「〜ということが、よくあります」
- 「よく言われるのが、〜です」
- 「ここ、ご覧いただけますか」
- 「正直に申し上げますと」

一つの記事に3〜4回入れるだけで、人が話している感じになります。

### 「お客様の声」の形にすると、押しつけが消える

課題の指摘は、自分の主張として書くと押しつけになります。
他社の実例として書くと、同じ内容でも受け入れられます。

| いまの書き方 | 営業マンなら |
|---|---|
| 現場のせいにされます | 「現場が使ってくれない」とよくご相談をいただきます |
| 三か月後には誰も使っていない | 三か月で止まってしまった、というお話をよく伺います |

## 第4部　実機で確認すべきこと

このレポートは資産マスターの記載との照合です。
次の項目は、実際に開いて確かめないと確定できません。

| # | 確認すること | どの記事に影響するか |
|---|---|---|
| 1 | 写真の上限は本当に5枚か | 建設 |
| 2 | 製造で自社の文書を入れる画面が公開されているか | 製造（記述の削除が必要かも） |
| 3 | 製造の工程・品質・記録が別URLで開けるか | 製造 |
| 4 | 音声入力がiPhoneのSafariで動くか | 医療介護・保育 |
| 5 | 小売で自社FAQを入れる際にコードが必要か | 小売（登録不要の記述） |
| 6 | 各デモがスマホで崩れずに開くか | 6本すべて |
| 7 | デモから記事に戻れるか | 6本すべて |

**特に2と4は、記事の文面を変える必要が出る可能性があります。**
先に確認してから公開したほうが安全です。

---

## 直す順番

1. **実機の確認（上の7項目）** ― ここが決まらないと文面が確定しない
2. **「デモ」を全記事で言い換える**
3. **デモの直前に「最初にこれを押してください」を一行足す**
4. **製造を書き直す**（タイトルと、自社文書の記述）
5. **音声入力の案内を医療介護・保育に足す**
6. **営業の日本語に寄せる**（第3部）

1から3までで、デモまでたどり着く人の数はかなり変わるはずです。
文章の質を上げるより、そちらのほうが先に効きます。
