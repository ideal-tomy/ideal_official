- 作成日: 2026-11-10
- 状態: 計画のみ。コード・設定・DNS・送信試験は未実施
- 対象: https://www.axeon.jp/ （リポジトリ `ideal-tomy/rinopro-site`）
- 根拠: 同フォルダの `01`〜`06`、横断表 `../02-risk-register.md`、`../axeon-dependency-audit.json`
- 監査時点の参照コミット: `62c55fa4c6a18bce324f0bae0138297161410a54`（公開 main と一致。本番デプロイとの一致は未確認）

この文書は、監査で「問題あり」とされた項目と、安全と断定できない未確認項目について、何をどの順で行うかを決めるためのもの。実装は別途承認してから着手する。

## 1. 前提

監査はソースの静的読解と、少数の公開 HTTP / DNS と依存監査まで。本番への送信、設定変更、WAF の解除はしていない。

次の区別を崩さない。

- コード上の問題と、本番で悪用できていることは別。
- Cloudflare の 403 は、全 API が守られている証拠にしない。
- 未確認の項目は「問題なし」にしない。
- 秘密の値（API キー、トークン、パスワード）は計画にもチャットにも載せず、項目名と環境名だけを確認する。
- ideal の問い合わせ 503 維持、トーナメント、サンリットは対象外。

## 3. 進め方

実装は小さく分け、1 回の変更で 1 つの問題を閉じる。外部設定とコード変更は混ぜない。

### フェーズ 0 — 本番の帰属を読む（変更なし）

高重大度を「本番で今こうなっている」と確定するための読み取り。値は伏せ、項目名と環境名だけを残す。

確認する項目:

1. `axeon.jp` / `www.axeon.jp` の Cloudflare 403 が、WAF・Bot Fight・国別制限・Access のどれか。API パスも同じルールか。
2. そのゾーンの先にある Vercel project、Production の branch と commit、Preview と Production の環境変数の分離（値は見ない）。
3. Resend の送信元ドメイン、`CONTACT_FROM_EMAIL` のドメイン、DKIM、日次 quota、抑止リスト、配信ログの保持。
4. Sanity の dataset 公開範囲、Studio メンバー、書き込み token の有無、公開 query が返す項目。デモデータに実顧客情報が混ざっていないか。
5. 問い合わせログと AI エラーログを、誰がどの期間見られるか。

ここで本番 commit が監査対象と違うと分かった場合は、A-01〜A-04 の根拠行をその commit で読み直してから実装する。

### フェーズ 1 — コードで閉じる（A-04 → A-03 → A-02）

本番権限がなくてもリポジトリで進められる。反映はフェーズ 0 で project が分かってから。

### フェーズ 2 — 自動返信の悪用面を狭くする（A-01）

体験を残すか、自動返信を止めるかを決めたあと。レート制限の保存先に新しいサービスを足す場合は、その前に承認を取る。

### フェーズ 3 — 依存関係（A-06）

フェーズ 1 とは別の変更にする。`npm audit fix` の一括適用はしない。

### フェーズ 4 — メール認証と運用（A-05、未確認の棚卸し）

正規送信（Google、Cloudflare Email Routing、Resend）の SPF / DKIM が揃ったあと、DMARC を段階的に強める。保持期間、復元、メンバー権限は運用責任者と定義する。

## 4. 各項目の対策

### A-01 任意アドレスへの自動返信

現状は `/api/contact` が Zod で形を見たあと、管理者通知と自動返信を `Promise.all` で送る。制限はプロセス内の Map で、同一 IP あたり 60 秒に 30 回。サーバーレスではインスタンスごとに Map が分かれ、`x-forwarded-for` はプラットフォームが付与した値以外を信用できない。CAPTCHA、メールアドレスの所持確認、宛先ごとの上限はない。片方だけ成功しても 502 になり、再送で重複し得る。

推奨は、自動返信を残したまま次を入れること。

1. 送信前に Cloudflare Turnstile を通す。サイトはすでに Cloudflare 配下なので、アプリ単体の honeypot より先にこれを使う。秘密鍵はサーバーだけで検証する。
2. 制限をプロセスメモリから外し、全インスタンスで共有する。保存先は Cloudflare のレート制限か、既存のキーバリュー。新規パッケージや外部サービスは導入前に説明する。
3. IP は、Vercel / Cloudflare が付与する接続元だけを使う。クライアントが付けた `x-forwarded-for` の先頭は識別子にしない。
4. 上限を三つに分ける。IP、宛先メールアドレス、サイト全体の日次送信数。全体上限は Resend の quota より手前で止める。
5. 管理者通知と自動返信の成否を分ける。成功した側は再送しない。利用者には受付と返信メールの成否を分けて返す。
6. 件名と本文は、今どおり text のみ。名前とメールに改行が残らないことを Zod で拒否する。

代替案は、自動返信をやめ管理者通知だけにすること。第三者への送信面はなくなる。問い合わせ者への即時返信もなくなる。

受入条件:

- モック送信先で、Turnstile 失敗・上限超過・改行入りメールが 1 通も出ない。
- 同じ宛先への連打が、プロセスを分けても上限を超えない。
- 管理者だけ成功、返信だけ成功、の両方で重複送信が起きない。
- 本番アドレスへは送らない。

### A-06 既知脆弱性の該当版

`next@16.2.0` は、監査 JSON 上、Server Components の DoS、Image Optimization（AVIF / SVG）、`next/og`、Windows ホスト上の RCE、`use cache` などの勧告 range に入る。`sharp@0.34.5` も該当版。critical の集計には推移的な `proxy-addr` と `tar` も含まれる。

対応:

1. 勧告ごとに「このアプリの到達条件」を表にする。画像最適化の公開、`images.remotePatterns`（現状は `cdn.sanity.io`）、`next/og` の使用、`use cache` の使用、ホスティング OS。
2. 到達するものから、修正版へ上げる。上げ先の版番号は着手時の勧告 range で決め、この計画には固定しない。
3. Next.js の更新は単体の PR にし、`npm run build` と主要画面（トップ、問い合わせ、チャット、デモ、Studio）を見る。
4. 開発依存だけの指摘は、そのツールを本番や公開 CI で動かしていないことを確認したうえで後回しにする。
5. デプロイは、フェーズ 0 で Production project が特定できてから。未特定の間はリポジトリの更新までに留める。

受入条件:

- 上げた版が、到達すると判定した勧告の修正 range に入っている。
- ロックファイルを更新し、本番ビルドの版と一致している。
- 画像と Sanity 画像の表示が壊れていない。

### A-02 個人情報のログ

`/api/contact` は本番でも氏名・メール・会社名を `console.info` する。開発時は本文と添付のプレビューも出す。問い合わせ本文は Resend と受信者へ渡るが、ログは別の保管場所になる。

対応:

1. 本番ログから氏名、メール、会社名、本文、添付プレビューを外す。残すのは受付 ID、本文の文字数、付随データの有無、送信結果だけ。
2. 開発時の全文プレビューはローカル開発だけにする。Preview のログが残るなら、Preview でも出さない。
3. Vercel のログ閲覧者と保持日数を決める。決めるまでは「コードから消す」までを完了とする。

受入条件:

- 本番相当の環境変数で問い合わせをモック送信し、ログに氏名・メール・会社名・本文が出ない。
- 送信失敗の調査に必要な結果コードは残る。

### A-03 AI API の入力上限

`/api/chat` は配列であることだけを見て `UIMessage[]` として扱い、件数も文字数も見ていない。`/api/estimate-detailed` は型アサーションだけで、回答オブジェクトの大きさに上限がない。同じ不足は `/api/demo/run` と `/api/experience/knowledge-bot` にもある。`/api/inquiry-brief` は Zod がある。`/api/demos/recommend-from-text` は 2000 文字で切っている。

対応:

1. Gemini を呼ぶ route すべてに、共通の上限を置く。会話件数、1 メッセージの文字数、リクエスト全体のバイト数、見積回答のキー数と各値の長さ。
2. 上限超過は 400 で返し、モデルは呼ばない。
3. `maxDuration`（現状 60 秒）と `maxOutputTokens` は維持し、入力側で先に止める。
4. カタログ GET は入力がない。返す項目が公開してよいものだけかを、フェーズ 0 の Sanity 確認と一緒に見る。

受入条件:

- モックしたモデル呼び出しで、件数超過・巨大文字列・想定外の型が Gemini に届かない。
- 通常のコンシェルジュ、見積、デモ 1 往復は今までどおり通る。

### A-04 内部エラーの返却

次の route が `err.message` をそのまま JSON で返している。

- `/api/chat`
- `/api/inquiry-brief`
- `/api/estimate-detailed`
- `/api/demo/run`
- `/api/experience/knowledge-bot`

対応:

1. 利用者へ返す文は固定する（例: 処理に失敗した、時間をおいて再度）。
2. 例外の中身はサーバーログだけに残し、リクエスト本文はログに混ぜない。
3. 問い合わせ API はすでに固定文なので、ここには含めない。

受入条件:

- モデル呼び出しを失敗させたとき、応答本文にプロバイダ名、キー、スタック、内部 URL が含まれない。

### A-05 DMARC

公開 DNS では SPF が 1 レコード（`google` / `cloudflare` / `resend` の include、`~all`）。DMARC は `p=none`。DKIM と実 From は未確認。`p=none` の間は、なりすましを隔離・拒否する指示にならない。

対応:

1. フェーズ 0 で、Resend のドメイン認証と実際の From、Cloudflare Email Routing、Google 送信の DKIM が揃っていることを確認する。
2. 揃うまでは `p=none` のまま、集計用レポートアドレスだけ先に足すかを決める。
3. 正規メールがすべて認証を通ったあと、`quarantine` を経て `reject` を検討する。失敗した正規メールが出たら強化を止める。
4. SPF の include 展開数が上限を超えていないかを、強化前に数える。

受入条件:

- 変更後の TXT を公開 DNS で再取得し、意図したポリシーと一致する。
- 管理者通知と自動返信の認証結果が pass である（試験は承認した隔離先だけ）。

### 未確認（問題 ID なし）

安全とは扱わず、フェーズ 0 と 4 で閉じる。

| 項目 | 対応 |
|---|---|
| CSP が `unsafe-inline` と `unsafe-eval` を許可 | 本番応答ヘッダーと `next.config.ts` を照合し、Studio と LP に必要な許可だけ残す。`frame-ancestors 'none'` は維持 |
| Studio の path が公開 | 画面が見えることと編集できることは別。メンバーと token 権限を確認する |
| 公開 API にログインがない | 匿名受付が仕様。権限の代わりに、入力上限・共有制限・予算で守る |
| Gemini の予算とログ | provider の project、日次上限、ログ保持を確認し、アプリの全体上限と揃える |
| Sanity のバックアップと削除 | 復元手順と、公開不要な項目の有無を dataset ごとに書く |
| GitHub が public | 秘密が履歴に無いことを確認する。公開そのものはこの計画では変えない |

## 7. 着手前に決めること

1. 自動返信は残す（Turnstile と上限付き）か、管理者通知だけにするか。推奨は残す。
2. 共有レート制限の置き場所は Cloudflare か、アプリ側のキーバリューか。新規サービスを足す場合は、理由と費用を見てから承認する。
3. A-06 の Next.js 更新を、フェーズ 1 の修正より先に出すか後に出すか。推奨は後。脆弱性の到達条件の表だけ先に作る。
4. フェーズ 0 を見るアカウント（Vercel、Cloudflare、Resend、Sanity）の読み取り権限を、誰が持っているか。

## 8. 戻し方

コード変更は PR 単位で戻す。DNS と WAF は変更前の値を控えてから行い、正規メールの不達が出たら直前の値に戻す。依存更新でビルドが壊れた場合は、その PR だけを戻し、フェーズ 1 の修正は残す。
