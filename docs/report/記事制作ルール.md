# 業界記事HTML・デモ制作ルール

> **2026-08-23:** 記事のページ構成・セクション順はこのファイルに固定しない。都度の確認は `.cursor/rules/article-is-one-off.mdc`。何を読むかは [記事の読み順.md](./記事の読み順.md)。本書は判定・言葉・デモとの関係・法令の保守に使う。「形のレシピ」を全記事のテンプレにしない。

建設記事の完成までに分かったことを、次から必ず守る決まりとしてまとめたもの。
新しい業界の記事を作るときは、必ず最初にこれを読む。

---

## 0. いちばん大事な前提

**記事の第一目的は、知識を渡すこと。デモはその知識を確かめてもらう道具。**

順番を逆にすると、必ず失敗する。デモへ誘導することを目的にすると、
記事の主語が「IT導入」になる。IT導入は業界に関係のない話なので、
どの業界で書いても同じ形になる。**これがテンプレート化の唯一にして最大の原因。**

実際、最初に作った6本は全部この失敗をしていた。

- 建設 … 導入したものが定着しない話
- 製造 … 導入が決まらない話
- 医療介護 … 導入したのに楽にならない話
- 保育 … 導入した機能が多すぎる話
- 小売 … 導入がうまくいかない話
- 飲食 … 導入したものが増えすぎた話

色も図も書体も全部変えたのに、テンプレートに見えた。中身が全部「導入」だったから。

---

## 1. 記事の中身を決める手順

### 1-1. 主語を「その業界の仕事そのもの」にする

ITの話ではなく、業界の実務の話を書く。

| 業界 | 書くこと（例） |
|---|---|
| 建設 | 工事写真の撮り方と整理のしかた |
| 製造 | ベテランから作業の勘どころを聞き出す方法 |
| 医療介護 | 記録と制度の関係。何を残す必要があるか |
| 保育 | 先生の時間がどこに消えているかの数え方 |
| 小売 | 問い合わせの分類のしかた |
| 飲食 | シフトの組み方の原則。何時間前に何を決めるか |

**判定方法**：その記事から、デモへのリンクを全部消す。
それでも読む価値が残っていれば合格。残らなければ、まだ導入の話を書いている。

### 1-2. ITがなくても明日できることを、必ず一つ以上書く

建設なら「着工前に撮影箇所の一覧を紙一枚で作って配る」。
これがあると、記事が本物になる。売り込みではなく助言として読まれる。

### 1-3. 法令・基準・制度を調べて盛り込む

いちばん差がつく部分。ここを調べていない記事は、どこにでもある記事になる。

建設の例：
- 電子小黒板は平成29年に国交省が利用を認めている
- 改ざん検知の機能が必須。納品時に確認結果も提出する
- 画像の回転や明るさ補正を含む一切の改変が禁止
- 2024年4月の時間外労働の上限規制

**必ず出典URLを記事末に置く。**社内で回してもらうときに効く。

### 1-4. 効率化の話を、最後に人の話へ着地させる

数字だけで終わらせない。建設では、

```
撮影が二人から一人になる（人工）
事務所の入力がなくなる（残業）
　↓
事務所から現場への電話が消える（職場の空気）
```

最後の一つに、いちばん分量を割く。
「どちらも悪くないのに、毎日それが起きている」という書き方をする。
現場と事務所、店長とスタッフ、といった**社内の摩擦**は、どの業界にもある。

## 2. 記事の形は、中身から決まる

**先に型を決めない。**中身を決めれば、形は自然に出てくる。

これまでに出てきた形：

| 記事 | 形 | なぜその形か |
|---|---|---|
| 建設 | 時間順（着工前 → 現場 → 事務所） | 手順の記事だから |
| 飲食 | 表を先に見せて、そこから説明 | シフト表が主題そのものだから |
| 保育 | 数が減っていく（12 → 3 → 1） | 機能を絞る話だから |
| 小売 | 一覧を10件並べて7件と3件に割る | 分類の記事だから |

### 骨格は作業順。形の見た目は再利用しない

章の並びは、現場の人がやる作業の順番にする（撮る前→撮るとき→撮ったあと、台帳を作る→実施日に書き直す、など）。
**建設の①②③（`.phase`）は、建設の中身から出た形なので、他記事にコピーしない。**
各記事は、すでに持っている実物（受信箱、シフト表、点検台帳、差異伝票など）を表紙に残し、形は記事ごとに別のままにする。

### 使ってはいけない型

**「原因は二つあります → 理由その1 → 理由その2 → だからこうする」**

建設と飲食で2回使った時点で、これは型になった。もう使わない。
他の形も、二度使ったらその時点で禁止にする。

**「再定義 → 分類の正しさ → 印象的な締め」**も使わない。軸や用語を先に教えてから作業に入ると、途中から読めなくなる。

### 章の数と長さを揃えない

- 建設 … 10分（実務の手順記事）
- 飲食 … 6分
- 保育 … 5分

揃えると、それだけでテンプレートに見える。**内容が要求する長さにする。**

### 締めの文を使い回さない

最初の6本は、全部これだった。

> 「〜だけ教えていただければ、どこから手をつけられるかは見当がつきます」

穴埋め部分だけ違う同じ文。**締めは記事ごとに完全に書き下ろす。**

## 3. 日本語の決まり

### 3-1. 営業の日本語で書く。評論家の日本語で書かない

違いは主語。評論家は現象を主語にする。営業は相手を主語にする。

| 書かない | こう書く |
|---|---|
| 導入したのに三か月後には誰も使っていない | 「入れたのに、三か月で誰も使わなくなった」というお話をよく伺います |
| たいてい現場のせいにされます | どうしても現場のせいになりがちです |
| 〜という話ではありません | 〜ではありません。ここは正直に申し上げます |
| 見るべきは補助率ではなく | 補助率より先に見ていただきたいのは |
| 教えてもらえれば | 教えていただければ |
| 使われません | 使ってもらえません |

### 3-2. 言い切るものと、和らげるもの

**言い切る**
- デモで何ができて、何ができないか
- 自分たちの姿勢（ここは正直に申し上げます）

**和らげる**
- 相手の会社の状況の決めつけ
- 相手が過去にやったことの否定

逆にしない。実例：

> ✕ その工程は会社の資産ではなく、その人の私物になります
> ○ その方が休まれると止まってしまう。教えようとしても、うまく伝わらない

### 3-3. 使わない言葉

- **DX、ICT** … 一度も使わない。「新しい仕組み」「記録ソフト」など具体物の名前で書く
- **FAQ、エスカレーション、形式知化、属人化、KPI** … 普通の日本語に置き換える
- **「〜の正体」「軸」** … 気取った言い回し
- **「デモを開く」** … 「動かしてみる」に統一
- **カタカナの言い換えが通じる場面でも、業界で実際に使われている語を優先する**
  （POS、小黒板、要録などは、その業界の人には通じるのでそのまま使う）

### 3-4. 見出しは、読んだだけで中身が分かること

記事タイトル（h1）も、セクション見出し（h2）も同じ。

| ✕ | ○ |
|---|---|
| その工程を説明できる人は、あと何人ですか | 製造業で、システムの導入が決まらない理由 |
| 「うちの現場には合わない」は、正しい | 工事写真の整理が終わらない理由と、その直し方 |
| 残りの二つは、手当てが抜けているだけです | 発送したら知らせる。在庫は要る画面に置く |
| いちばん消えるのは「聞いていた時間と違う」です | 雇うときに、働く時間の幅を書いて渡す |
| ここまでやると、何が変わるか | （作業名にする。結論は本文の太字へ） |

**セクション見出しは作業の名前にする。**「だから／残り／いちばん／ここまで」など、前の節を指す語を入れない。結論や警告は本文の太字に移す。

**質問だけを投げる見出しは使わない。**答えを知らない人には意味が取れない。
読者の言葉をそのまま見出しにするのも避ける。本文の中で引用として使う。
締めの見出しを「〜しませんか」に揃えない。締めの文は記事ごとに書き下ろす。

### 3-5. 話し言葉を1記事に3〜4回混ぜる

「よくお聞きするのが」「正直に申し上げますと」「ここは必ずご確認ください」。
全文がきれいな書き言葉だと、人が話している感じにならない。

## 4. デモとの関係

### 4-1. デモは記事の途中に置く。最後ではない

読んで分かったことを、その場で確かめてもらう位置に置く。
建設では③の章の中に置いた。

**記事の内容を最後まで書き切る。**
「ここから先は触ったほうが早い」で切らない。書き切った記事のほうが社内で回される。

### 4-2. デモでできることと、記事の説明を必ず突き合わせる

書く前に、そのデモの実物を確認する。以下は実際に起きたずれ。

- 記事「写真を整理して報告書に」→ デモは5枚まで。読者は数百枚を想像する
- 記事「自社の文書を入れて試せます」→ その画面が公開されているか未確認だった
- 記事「その場で声に出す」→ 音声入力はブラウザ依存。iPhoneで動かない可能性

**制限は先に書く。**「まずは5枚ほどでお試しください」と書いてあれば、5枚でも試してもらえる。

### 4-3. 正直に書く。隠さない

- AIではなく決まったルールで計算している → そう書く
- まだAIにつないでいない試作 → そう書く
- その業界向けの画面ではない → そう書く（保育で介護の画面を見せた例）

**正直に書いた部分は、太字や枠で目立たせる。**弱点ではなく信頼材料になる。

### 4-4. 適用範囲の線引きを必ず書く

建設の例：

> こちらは社内の報告書や朝礼メモを作るためのものです。
> 公共工事の納品用の写真台帳は、改ざん検知に対応した専用のソフトをお使いください。

これを書くと「分かっている会社だ」と伝わる。書かないと誤解されて後で揉める。

### 4-5. デモの直前に、必ずこの3点を書く

```
何で動くか　　こちらで用意した◯◯で動きます
自分のデータ　お手元の◯◯を入れて試すこともできます
所要と登録　　2分ほどで終わります ／ 登録は要りません
```

### 4-6. 最初の一手を指定する

ITに慣れていない人は「どこを押せばいいか」で止まる。
「まず、青いボタンで写真を3枚選んでください」のように書く。

## 5. 図解の決まり

### 5-1. 1記事に2〜3個。それ以上入れない

4つ以上入れると、図を眺める記事になって実務の中身が頭に残らない。

### 5-2. 意味を、図形の物理的な関係に変える

言葉をアイコンに置き換えるのではない。

| 意味 | 形 |
|---|---|
| 詰まっている | 途中だけ細くなる |
| 二人でやっている | 同じ道を線が2本通る |
| 空欄が電話を生む | 空欄の数だけ線が伸びる |
| 一人休むと崩れる | 表の1コマが欠けて、他のコマが動く |
| 機能が多すぎる | 札が12個並んで、9個が薄くなる |

### 5-3. ラベルを全部消して、意味が残るか

残らなければ作り直す。これが唯一の合否判定。

### 5-4. 1記事の中で、図の形をすべて変える

流れの太さ／道すじの本数／空欄から出る線。同じ形を2つ入れない。
記事をまたいでも、同じ形は使わない。

### 5-5. やらないこと

- 概念ごとにアイコンを1個置いて矢印で結ぶだけの図
- 毎回Before-Afterにすること（1記事に1回まで。できれば0回）
- 箱を大量に並べる構成
- 装飾だけのアイコン・破線
- 本文が一段落しかない内容を図にすること（図のほうが重くなる）

### 5-6. 比喩は世間で定着しているものだけ

ファネル、ボトルネックのように定着したものは可。
独自の比喩は「その比喩が何を指すか」の説明が要るので不可。

### 5-7. 図の書式

- SVGで書く。viewBoxは横360前後にして、スマホで等倍になるようにする
- 図の中の日本語フォントは Noto Sans CJK JP
- 図の上に小さいラベル（図1、何の図か）、下に2〜3行の説明を置く
- 図の中の文字は最小10px相当まで。それより小さくしない

## 6. デザインの決まり

### 6-1. 文字サイズの幅を大きく取る

いちばん大きい文字と小さい文字の差を**4倍以上**にする。
差が2〜3倍しかないと、意図のないページに見える。

建設記事の例：

| 用途 | PC | スマホ |
|---|---|---|
| 見出し（h1） | 37px | 26px |
| 段階の見出し | 29px | 23px |
| セクション見出し | 26px | 21px |
| 項目の見出し | 17px | 16px |
| 本文 | 16px | 15.5px |
| 図の説明・注記 | 12.5px | 12px |
| ラベル（英数） | 10〜11px | 同じ |

### 6-2. 中央寄せにしない

見出しも本文も左揃え。中央寄せにしていいのは、ごく一部の見出しだけ。
**すべて中央寄せは、テンプレートに見えるいちばんの原因。**

### 6-3. 3等分に並べない

3つ並べると、どれも同じ重要度に見えて、どれも残らない。
1つ大きく、2つ小さく。または縦に並べて、1つだけ強くする。

建設では、効果の3項目のうち3つ目だけ文字を大きくして、上に色の線を引いた。

### 6-4. カードを乱用しない

白い角丸＋枠線に全部入れると、意味が消えて模様になる。
**カードを使うのは「他と切り離せる一塊」のときだけ。**
説明文や手順は、背景に直接置く。区切りは細い罫線と余白で作る。

### 6-5. 色は3色まで

- 本文の色
- 面の色（1色）
- 強調の色（1色）

建設は、紙色・紺・朱の3色。これ以上増やすと締まらなくなる。

### 6-6. 動きは1ページに1つだけ

建設は赤い書き込みが下から出てくるだけ。
飲食はシフト表の1コマが「欠」に変わるだけ。
2種類以上の動きを入れると、安っぽくなる。

必ず `prefers-reduced-motion` に対応し、動かない場合は最終状態を最初から出す。

### 6-7. 必ず入れる技術的な指定

```css
/* iOSダークモード対策（3層） */
<meta name="color-scheme" content="light">
:root{ color-scheme: light only; }
@media (prefers-color-scheme: dark){ /* ライトの色を明示的に上書き */ }

/* 日本語見出しの改行崩れ対策 */
h1,h2,h3{ word-break:auto-phrase; line-break:strict; text-wrap:balance; }
```

- iPhoneの横幅370pxを基準にレイアウトを確認する
- 本文の1行の幅は最大620px前後
- 行間は1.9前後（読ませたい記事は2.0まで広げる）

### 6-8. 業界ごとに見た目の「もと」を決める

その業界に実在する紙や道具から取る。装飾ではなく、意味のある選択にする。

| 業界 | もと | 書体 | 目印 |
|---|---|---|---|
| 建設 | 図面と赤ペンの書き込み | 明朝 | 右余白の赤い書き込み |
| 製造 | 工場の作業手順書 | 太ゴシック | 左の工程レール |
| 医療介護 | 申し送りノート | 細ゴシック・広い字間 | 横罫の紙 |
| 保育 | おたより | 見出し小・本文大 | 丸みと白 |
| 小売 | 問い合わせの受信箱 | 中ゴシック | 一覧の行 |
| 飲食 | 週のシフト表 | 太ゴシック | 表そのもの |

### 6-9. 表紙・実物・図版・スタンプ（ページの質量）

ストック写真や人物写真は入れない。コンサルの事例カタログにもしない。
最初の画面で「何の実務ノートか」が物として分かるようにする。

1. **表紙** — 業種名＋読む分＋法令確認日を、11pxのメタではなく表紙の一部にする
2. **仕事の実物** — ヒーロー内（または直後）に、その仕事の紙・表・受信箱を置く。飲食のシフト表が基準
3. **図版** — `.figure` は白カード（背景・枠・内側余白）にしない。ラベル＋図＋キャプションだけ。幅は本文より広く
4. **出典スタンプ** — 末尾の参考はそのまま。本文の法令・基準の一文の横に、既存出典への短いスタンプを1つ置く（新しい主張は足さない）

やらないこと:

- ストック写真、人物写真
- 英語セクションラベル（Point of View 等）
- 事例のない実績枠
- 9本のヒーローを同じレイアウトに揃えること

---

## 7. 書かないこと（全記事共通）

- 効果を大きく見せる書き方（「不良ゼロ」「完全自動化」「◯%削減」）
- 出どころのはっきりしない他社の数字
- 人を減らせるという書き方（減らすのは、往復と手戻り）
- 補助金を主題にすること（補助金の記事として読まれ、本題まで進まない）
- 人手不足・2024年問題を書き出しに置くこと（どこも書いていて飽きられている。出すなら後半）
- 相手の会社の文化や職人のやり方を悪く言うこと

## 9. 法令を扱うときの決まりと、保守

記事の強さは法令や公的な基準を調べて書いているところから来ている。
同時に、いちばん壊れやすいのもここ。改正が入ると、記事が一気に嘘になる。

### 9-1. 一次資料を必ず当たる

- 出典は官公庁・自治体のページやPDFを優先する
- 解説記事は、理解のために読むだけ。出典としては二番手に置く
- 解説記事の数字をそのまま書かない。必ず元の資料で確かめる

### 9-2. 事実と意見を、文のレベルで分ける

| 種類 | 書き方 |
|---|---|
| 法令で決まっていること | 「〜と定められています」「〜が義務になりました」 |
| 自治体や業界の一般的な運用 | 「〜とされています」「多くの自治体では〜」 |
| こちらの提案 | 「〜をおすすめします」「〜のほうがいいと思います」 |

混ぜない。読者が「これは守らないといけないのか、そちらの意見なのか」を
迷った時点で、記事の信用が落ちる。

### 9-3. 法令の部分は、見た目で区別できるようにする

囲みや枠に入れて、本文と分ける。理由は二つ。

- 読者が「ここは決まりごとだ」と分かる
- **見直すときに、どこを直せばいいか探せる**

後者が保守で効く。本文に数字が散っていると、改正のたびに全文を読み直すことになる。

### 9-4. 記事に二つの日付を出す

```
2026.08　／　法令の確認 2026.08
```

公開日と、法令を最後に確かめた日は別物。分けて出す。
古い記事でも、確認日が新しければ読者は安心して読める。

### 9-5. 法令台帳を一枚持つ

記事が増えるほど、どの記事がどの法令に触れているか分からなくなる。
一枚の表で管理する。

| 記事 | 法令・基準 | 触れている内容 | 最終確認日 |
|---|---|---|---|

### 9-6. 見直しの決まり

- **年に一度、全記事の法令部分を見直す日を決める**（例：毎年4月）
- 改正の情報が入ったら、その場で該当記事だけ直す
- 直したら、記事の「法令の確認」の日付を更新する
- 直さなかった記事も、確認したなら日付だけ更新する

年に一度の見直しを「やろうと思っている」状態にしない。日付を決めて予定に入れる。

### 9-7. 免責の一文を入れる

記事の末尾、出典の手前に置く。

> 制度の内容は改正されることがあります。実際の対応にあたっては、
> 所管の官公庁や自治体の最新の情報をご確認ください。

長く書かない。一文で足りる。書いていないと、間違えたときに逃げ場がなくなる。

### 9-8. 数字は本文に散らさない

法令の数字（何日、何%、何年）は、囲みの中にまとめる。
本文には「さきほどの期間」のように受ける形で書く。
こうしておくと、改正のときに直す場所が一か所で済む。
