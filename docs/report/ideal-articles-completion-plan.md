## 0. 完成の定義

次が揃ったら、idealの記事体験は完成とする。

1. ハブが「業界」と「仕事の詰まり」の短い目次になっている
2. 9本の業界記事が、元HTMLの色・図・紙の見た目で読める
3. 図は本文より広く、段階見出しの余白が普通のh2より大きい
4. デモがある記事は実URL・別タブ・最初の一手がある。無い記事は知識のまま相談へ
5. テーマ記事は、AXEONの5見出しではなく、仕事の名前で0〜3本（後追い可）
6. 受けないラインはハブに並べず、デモ直前と問い合わせだけに置く

AXEONのテーマ5＋業界5＋境界は、idealの目次にしない。

## 2. 公開の骨格（ideal）

```
/articles
  業界から　　建設　製造　医療・介護　保育　小売　飲食　ビルメン　運送　倉庫
  詰まりから　写真が終わらない　手順が残らない　記録がずれる　…

/articles/{slug}     業界記事（主）
/articles/t/{slug}   テーマ記事（仕事名。後追い）
```

ハブの題は短い名前。全文のh1は記事側に残す。  
3等分カード・中央寄せ・「自動化」「ナレッジ活用」ラベルは使わない。

詰まり → 記事の対応:

| 短い名 | slug |
|---|---|
| 写真が終わらない | construction |
| 手順が残らない | manufacturing |
| 記録がずれる | care |
| 何かあった日の記録 | childcare |
| 問い合わせが減らない | retail |
| シフトでもめる | restaurant |
| 点検が漏れる | building |
| 守れているか分からない | logistics |
| 数が合わない | warehouse |

テーマ記事を足すときも、この「詰まり」列に1行足す。AXEONの「AI業務アシスタント」等は使わない。

## 3. フェーズ

### P0 見た目と入口（サイト内だけで完了）

idealを先に完成させる本体。デモ新規開発を待たない。

1. **ハブを2群の短い目次にする**
   - ファイル: `app/articles/page.tsx`、`components/articles/ArticleHubList.tsx`、`data/articles/index.ts`
   - 業界を主、詰まりを従。同じ大きさの9カードにしない
2. **記事のメリハリ**
   - 公開HTMLまたは記事CSS: 本文〜620px、図は860〜940px
   - 段階見出し（①着工前など）の余白・字を、普通のh2より大きくする
   - 図の直後は1〜2文、次見出しまで空ける
   - サイトのパンくず／「ほかの記事」は細く。記事の紙色は端まで通す
3. **既存デモの穴**
   - シフト・ビルメン: 本番URLが分かれば `scripts/prepare-article-html.mjs` の `DEMO_URLS` と `EXTERNAL_DEMO_URLS` に足して `npm run prepare:articles`
   - 分からなければ準備中のまま（ダミー `#` は戻さない）
   - 製造の「自社文書を入れて試せます」は公開画面が無いなら削除済みを維持
4. **受け入れ**
   - `/articles` で業界名をクリックして記事へ
   - 建設・運送の図に朱／緑が付いている（グレー落ちしていない）
   - 図が本文より広い

### P1 未接続デモの実体（別リポジトリ可）

記事公開はP0で先に出す。デモは後追い。

| 順 | 対象 | 参照 |
|---|---|---|
| 1 | 倉庫：差異の原因分け | [運送と倉庫のデモ提案.md](./運送と倉庫のデモ提案.md) |
| 2 | 運送：判定できる時期のコックピット | 同上 |
| 3 | シフト・ビルメンの公開URL接続 | 既存デモのURL確定 |
| 4 | 保育：介護画面の借り物を、保育の言葉にするか、記事の最初の一手をさらに具体にする | 画面が無いなら正直枠を維持 |

新規デモは `@axeon/ai-demo-core`、テーマ別要件＋ Demo Definition。体験コードはポータルへ。  
ideal向けのコピーは「登録不要・1現場／1店・最初の一手」。AXEON向けの部門・権限文はこちらに書かない。

公開後: `EXTERNAL_DEMO_URLS` → `prepare-article-html.mjs` → `hasDemo: true`

### P2 テーマ記事（任意・少なく）

業界9本が主。テーマは、業界をまたいでも同じ仕事だけ。

候補（最大3、先に1本で試す）:

1. 問い合わせは、なぜ来たのかで分ける（小売記事を原型。職場は1社に固定）
2. 社内の決まりを、誰が休んでも辿れる（製造の聞き取りを原型）
3. 希望を集めてからシフトを決める（飲食を原型。介護・店にも一文）

書かない:

- AI導入・定着支援
- 業務プロセス再設計
- データ活用の汎用記事
- AXEONの「提供すること／受けないこと」を本文にした記事

1本書いたら、デモリンクを消しても読む価値が残るかで判定する。残らなければ捨てる。

## 4. 受けないライン（idealでの置き場）

社内基準としては持ってよい。公開ハブには出さない。

置く場所:

- 各記事のデモ直前（既存の正直枠）
- `/contact?intent=article`
- 必要なら `/services` の一文

中小向けの言い方: 「これは社内報告用です。納品台帳は専用ソフトで」のように、その仕事の線だけ書く。

## 5. AXEONとの関係

| 共有してよい | 分けて書く |
|---|---|
| デモのエンジン（写真→報告書、ナレッジ、CS、シフト、運送・倉庫） | ハブの見出し、ヒーロー、最初の一手 |
| 記事の実務知識（法令・手順） | ブランド名、請けない案件の前面出し |
| Core・体験コードポータル | テーマ5本のカタログ |

ideal完成後に、同じデモURLをAXEONの業種LPから開いてよい。記事HTMLの全文をAXEONに複製しない。向こうはテーマ＋境界が入口。
